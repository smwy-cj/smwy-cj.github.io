## 简介

在 RAG（Retrieval-Augmented Generation，检索增强生成）系统中，检索模块的任务是：**从外部知识库中找出与用户问题相关的资料，先一并加入上下文，最后交由LLM进行处理**。

最常见的两类方案是：

- **关键词检索（Keyword / Lexical Retrieval）**：根据查询词与文档中的词项匹配程度进行检索。
- **向量检索（Vector / Semantic Retrieval）**：将查询与文档表示为向量，根据向量相似度寻找语义相关的内容。

如今大部分 RAG 系统均采用两类方式**混合检索（Hybrid Search）**。

## 核心内容

### 1. 关键词检索：匹配“用了哪些词”

**基本原理：** 对文本进行分词或词项分析，利用**倒排索引（Inverted Index）**快速定位包含相关词项的文档，再按相关性排序。

假设知识库有以下内容：

| 文档 | 内容 |
| --- | --- |
| A | 大模型推理优化技术研究 |
| B | 大语言模型部署方案 |
| C | 数据库索引与查询优化 |

一个简化的倒排索引可以表示为：

```text
大模型 → [A]
推理   → [A]
优化   → [A, C]
数据库 → [C]
```

用户搜索“**大模型推理优化**”时，系统可以直接查找这些词项对应的文档，再计算相关性得分。实际中文检索效果会受分词器、词项归一化等因素影响。

**典型算法：BM25**。它综合考虑：

1. **词频（TF）**：查询词在文档中出现的次数；
2. **逆文档频率（IDF）**：查询词在整个文档集合中越少见，通常区分度越高；
3. **文档长度归一化**：避免长文档仅因包含更多词而获得不合理优势。

示意伪代码：

```python
# 伪代码：BM25 依靠词项匹配和统计信息排序
index = build_inverted_index(documents)
query_terms = tokenize("PD 分离推理优化")
results = bm25.search(index, query_terms, top_k=5)
```

**优势：** 无须 Embedding 模型；对函数名、API、错误码、论文中的**准确术语**等精确匹配场景通常表现较好。

**局限：** 对同义词、近义表达和跨语言表达不够敏感。例如查询“降低响应时间”，可能漏掉仅讨论“减少推理延迟”的文档。

### 2. 向量检索：匹配“表达了什么语义”

**基本原理：** 使用 **Embedding（文本嵌入）模型**把查询和文档转换为高维向量，再通过向量相似度或距离检索相关内容。

例如：

```text
查询：如何提高大模型推理速度？
文档：降低 LLM 推理延迟的方法
```

虽然词语没有完全对应，但两者讨论的是相近的问题，因此合适的 Embedding 模型可能将它们映射到向量空间中相近的位置。

常见的**余弦相似度（Cosine Similarity）**公式为：

$$
\operatorname{sim}(A,B)=\frac{A\cdot B}{\|A\|\|B\|}
$$

余弦相似度越大，表示两个向量的方向越接近；但**向量相似不等于事实正确或一定能回答问题**。

典型工作流程包括：

1. **离线建库**：文本切分 → Embedding → 将向量及原文存入索引；
2. **在线查询**：问题 Embedding → 相似度搜索 → 返回 Top-K 文档片段。

```python
# 伪代码：离线建库
for chunk in split_documents(documents):
    vector = embedding_model.encode(chunk.text)
    vector_index.add(vector=vector, text=chunk.text)

# 伪代码：在线检索
query = "怎样加快大模型生成回答的速度？"
query_vector = embedding_model.encode(query)
results = vector_index.search(query_vector, top_k=5)
```

向量库/索引的常见实现有 **FAISS**、**Chroma** 等；在大规模场景下，系统常使用近似最近邻（ANN）索引平衡速度、资源占用和召回率。

**优势：** 能够捕捉语义相近、措辞不同的内容，适合自然语言知识问答和论文检索。

**局限：** 需要额外的嵌入计算与向量存储；对于精确标识符、数字和罕见术语，可能出现“语义相似但细节不匹配”的情况。

### 3. 两种检索方式的核心区别

| 对比维度 | 关键词检索 | 向量检索 |
| --- | --- | --- |
| 关注点 | 词项是否匹配 | 语义是否接近 |
| 典型算法 | BM25、TF-IDF | Embedding + KNN / ANN |
| 核心索引 | 倒排索引 | 向量索引 |
| 同义表达 | 相对较弱，依赖扩展策略 | 通常更强，取决于 Embedding 模型 |
| 精确标识符 | 通常更可靠 | 可能遗漏或混淆 |
| 额外模型 | 通常不需要 | 需要 Embedding 模型 |
| 典型应用 | API、函数名、错误码检索 | 论文问答、语义知识检索 |

**举例：** 用户查询“怎样加快大模型生成回答的速度？”

- 文档 A：「通过 Continuous Batching 降低 LLM 推理延迟。」
- 文档 B：「大模型推理速度的用户满意度调查。」

关键词检索可能更容易匹配文档 B 的字面词语；向量检索则可能优先找到在方法上更相关的文档 A。**这是示意性的检索倾向，不代表所有模型或索引的实际排序结果。**

### 4. 混合检索：结合关键词与语义信息

为了兼顾精确词匹配与语义召回，RAG 经常采用 **Hybrid Search（混合检索）**：

```text
                  用户问题
                     │
              ┌──────┴──────┐
              ▼             ▼
       BM25 关键词检索   Embedding 向量检索
              │             │
              └──────┬──────┘
                     ▼
              RRF 排名融合
                     ▼
             Reranker 重排序
                     ▼
           Top-K 资料 → LLM
```

其中：

- **RRF（Reciprocal Rank Fusion）**：根据不同检索列表中的名次融合候选文档，避免直接比较量纲不同的原始得分；
- **Reranker**：进一步评估“文档是否能回答该查询”，对候选文档重新排序（可选）。

```python
# 伪代码：混合检索

def hybrid_retrieve(query):
    keyword_hits = bm25.search(query, top_k=10)
    query_vector = embedding_model.encode(query)
    vector_hits = vector_index.search(query_vector, top_k=10)

    candidates = reciprocal_rank_fusion(keyword_hits, vector_hits)
    ranked = reranker.rank(query, candidates)  # 可选
    return ranked[:5]
```

在 Agent 中，这个检索过程还可以封装为一个 `retrieve_knowledge(query)` 工具，由 Agent 根据任务需要决定何时调用、检索什么内容、是否再次检索。

### 5. 实际开发如何选择？

- **精确查询**（错误码、接口名、类名）：优先考虑关键词检索。
- **语义问答**（论文概念、自然语言知识搜索）：优先考虑向量检索。
- **领域知识库 / 代码库 RAG**：可以从混合检索开始，按实际评测结果决定是否保留重排序模块。

评估时应结合 **Recall@K（召回）**、**MRR / nDCG（排序质量）**、回答的证据忠实度，以及检索延迟和成本，而不是仅凭单个示例判断优劣。

## 总结

关键词检索和向量检索的本质区别是：**前者侧重“词是否出现”，后者侧重“意思是否接近”**。

- **BM25** 适合捕捉精确词项；
- **Embedding + 向量索引** 适合查找语义相关内容；
- **Hybrid Search + Reranker** 可以发挥二者的互补优势，但会增加系统复杂度与成本。

在 RAG 和 Agent 系统中，检索的最终目标不是找“看起来相似”的文本，而是**找出能够为当前问题提供有效证据的内容**。
